ABSTRACT

Manual academic credential archiving and physical document requisition workflows in educational institutions often encounter operational bottlenecks, misplaced request slips, unorganized tracking, and prolonged processing turnaround. Students frequently experience friction following up on critical institutional documents such as Transcripts of Records (TOR), Certificates of Enrollment (COR), Certificates of Grades (COG), and Certificates of Good Moral Character. Concurrently, registrar administrators must manually sift through disparate paper files and spreadsheets to verify student records and release credentials.

To solve these institutional problems, this study designed, engineered, and evaluated the Student Request Records System, a robust, responsive web application developed using PHP 8, MySQL/MariaDB, JavaScript, HTML5/CSS3, and Bootstrap 5. The platform establishes two secure role-based portals: a Student Portal and an Administrator Dashboard. Students can create authenticated accounts, submit digital document requisitions specifying categories, purposes, and optional supporting requirements, track queue progress in real-time through dynamic status badges (Pending, Approved, Rejected), and securely stream or download released official digital files. Administrators possess full Create, Read, Update, and Delete (CRUD) privileges over institutional student records, live multi-field filtering by program and year level, and an interactive review pipeline to confirm, decline with written feedback, or attach approved digital credentials.

Defensive web engineering standards were enforced throughout the system architecture, including Bcrypt cryptographic password hashing, parameterized MySQLi prepared statements preventing SQL injection, role-based authorization guards, and multi-tier file upload validators enforcing MIME signature verification, byte constraints, and Apache directory hardening. Functional testing confirmed a 100% pass rate across 15 core verification modules, proving the system's operational reliability, security integrity, and high effectiveness in replacing manual registrar queues.

Keywords: Student Record System, Document Requisition Pipeline, Role-Based Access Control, Web Application Security, PHP/MySQL, Educational Management Systems.

CHAPTER 1: INTRODUCTION

1.1 Background of the Study

In higher education institutions and secondary schools, the registrar's office serves as the central administrative custodian responsible for issuing, validating, and archiving official student academic documentation. Key documents handled by this office include Transcripts of Records (TOR), Certificates of Enrollment or Registration (COR), Certificates of Grades (COG), Certificates of Good Moral Character, Honorable Dismissals, and Diplomas. These credentials are foundational for students seeking scholarships, employment, licensure examination filing, and university transfers.

Despite the rapid evolution of information and communication technologies, many educational institutions continue to process document requisitions through traditional, paper-based workflows. Under manual arrangements, students must physically visit the campus, queue outside registrar windows, complete physical request forms, seek clearances across campus offices, settle cashier fees, and repeatedly return to follow up on document preparation. This outdated model creates severe physical congestion, high administrative overhead, human filing errors, and substantial turnaround delays that can span multiple weeks.

Furthermore, students who reside far from the physical campus or alumni pursuing remote professional opportunities experience extreme inconvenience when attempting to request vital credentials. Modern web application architectures provide the ideal medium to digitize and automate these interactions. The Student Request Records System was conceived to address these systemic inefficiencies by replacing physical paperwork with an automated, role-based web platform that provides transparency, data security, and end-to-end request lifecycle tracking.

1.2 Problem Statement

A comprehensive domain analysis of conventional registrar operations identified several critical challenges that impede organizational productivity:

  • Difficulty Managing Records: Physical file folders, paper index cards, and decentralized local spreadsheets make it difficult to organize student academic histories reliably, leading to misplaced folders and data corruption.
  • Slow Searching and Information Retrieval: Administrative personnel spend excessive time manually searching physical filing cabinets to verify whether a student is regular, irregular, active, or cleared for document issuance.
  • Lack of Real-Time Status Visibility: Students receive zero digital feedback once a request form is submitted. They cannot determine if a request is under review, cleared, approved, or rejected due to lacking clearances without standing in physical follow-up lines.
  • Manual Documentation Errors: Handwritten requisitions lead to illegible student numbers, misidentified degree programs, and incorrectly prepared credentials.
  • Absence of Secure Digital Credential Delivery: When documents are prepared, registrar staff have no direct, secure channel to furnish verified digital copies to authorized students online.

1.3 Objectives of the System

1.3.1 General Objective

The primary objective of this study is to design, develop, and deploy a secure, web-based Student Request Records System that automates institutional student record management and provides a transparent document requisition pipeline featuring real-time status tracking and secure digital file delivery.

1.3.2 Specific Objectives

To fulfill the general objective, the research set the following specific technical goals:

  1. Secure User Authentication System: To develop an authentication subsystem enforcing strict role separation between Students (standard users) and Registrar Personnel (administrators), secured via Bcrypt cryptographic password hashing.
  2. Comprehensive CRUD Functionalities: To build administrative management tools allowing authorized staff to Create, Read, Update, and Delete institutional student records with multi-criteria dynamic search and filtering.
  3. Self-Service Document Requisition Engine: To develop an intuitive student interface allowing learners to request specific academic documents (TOR, COR, COG, Good Moral, Clearance, etc.), submit stated purposes, and attach optional clearance documents.
  4. Lifecycle Status Tracking Engine: To implement real-time visual progress monitoring featuring standardized status classifications: Pending, Approved, and Rejected, accompanied by administrative feedback remarks.
  5. Secure Digital Credential Release Subsystem: To engineer a streaming controller that permits administrators to attach approved digital documents and enables students to safely view and download their verified credentials.
  6. Defensive Web Security Framework: To protect student personally identifiable information (PII) against SQL Injection (SQLi), Cross-Site Scripting (XSS), path traversal attacks, and unauthorized file execution via prepared statements and strict server-side upload filtering.

1.4 Scope and Delimitation

Scope of the System: The system encompasses two primary operational portals: (1) an Admin Dashboard intended for registrar personnel featuring complete student record management, statistical metric monitoring, dynamic multi-field search/filtering, and centralized file request review; and (2) a Student Portal for registered students to inspect personal academic demographics, upload profile portrait avatars, submit document requests, monitor approval status in real-time, cancel pending requisitions, and download approved digital credentials. Security controls include Bcrypt password hashing, parameterized queries, and defensive file streaming.

Delimitation of the System: The system is currently configured for deployment on single-campus environments running Apache, PHP 8, and MySQL/MariaDB. Automated payment gateway checkout (e.g., credit card or e-wallet integration for transcript fees) is excluded from the current scope; proof of payment/clearance is handled via optional file attachments. Automated SMS dispatch is reserved for future versions; alerts are currently communicated via live in-session flash messages and status badge updates.

1.5 Significance of the Study

The deployment of this system provides tangible operational value to key academic stakeholders:

  • To Students: Eliminates long physical queues, reduces travel expenses, allows 24/7 requisition submission, and provides continuous visibility into document processing status.
  • To Registrar Administrators: Reduces manual filing burdens, organizes requests into a unified digital queue, speeds up student record verification, and establishes clear digital audit trails.
  • To the Educational Institution: Modernizes campus administrative services, reduces paper and storage expenses, and elevates institutional operational efficiency.
  • To IT Educators and Researchers: Serves as a validated, standards-compliant architectural model demonstrating secure PHP/MySQL web application engineering and relational database normalization.

CHAPTER 2: SYSTEM CONCEPT AND DESIGN

2.1 System Description

The Student Request Records System is an enterprise-oriented web application designed to digitalize academic record workflows. Built around a role-based architectural pattern, the system presents tailored user interfaces depending on the authenticated role:

  • Student User Role: Authenticated students are directed to a dedicated self-service portal (`student_dashboard.php`). Here, students can view their recorded student ID, degree program, year level, and enrollment status. The portal features a "Request a File" modal where students select the desired document, declare their purpose (e.g., scholarship, job application, board examination), and upload optional clearance proofs. Submitted requests populate a live status queue with visual status indicators (Pending, Approved, or Rejected). Approved requests unlock one-click digital download buttons.
  • Administrator Role: Registrar officers are directed to the administrative management console (`dashboard.php`). Administrators monitor live institutional metrics (total enrolled students, regular vs. irregular counts, active file attachments, and pending requisition counters). The console includes advanced search and filtering tools, full student CRUD modals, and a dedicated "Student File Requests Management" section where staff can approve requests (and attach official digital credentials), reject requests with documented reasons, or remove records.

2.2 Reason for Choosing the System

The decision to select and develop this specific system was driven by widespread operational delays observed in university registrar environments. Document backlogs frequently create friction during graduation clearances and board examination deadlines. Developing an end-to-end web system that replaces static paper filing with a transparent, stateful requisition pipeline directly resolves administrative bottlenecks.

Furthermore, previous record systems often treated file uploads as static, admin-only fields. By decoupling student record management from document requests and introducing a dedicated file_requests relational architecture with Pending, Approved, and Rejected lifecycle states, the system empowers students with self-service autonomy while preserving institutional administrative authority.

CHAPTER 3: SYSTEM DEVELOPMENT

3.1 Development Process

The software development lifecycle was executed through five structured, iterative stages:

  1. Planning & Domain Requirements Analysis: Identifying operational bottlenecks in academic document processing, surveying registrar service protocols, specifying functional user stories for students and staff, and formulating database relationships.
  2. Database Creation & Dynamic Migrations: Establishing the relational schema in MariaDB. To eliminate manual database setup friction, automated self-healing scripts were implemented inside `db_connection.php` that programmatically create missing tables, add required columns dynamically, and seed default administrative credentials.
  3. Modular Coding: Writing clean, maintainable, object-oriented, and procedural PHP 8 scripts adhering to defensive programming guidelines. Frontend components were built utilizing Bootstrap 5 responsive structures and native ES6 JavaScript for dynamic DOM manipulation.
  4. Defensive Testing & Verification: Executing unit test scripts, boundary checks on file upload limits, cross-role authorization checks, and security penetration scripts simulating SQL Injection and path traversal.
  5. Debugging & Refactoring: Addressing discovered edge cases—such as cascade file unlinking when student records are deleted, handling non-standard image MIME containers, and synchronizing request status badges.

3.2 Security Implementation

Securing student personally identifiable information (PII) and institutional academic records was a primary architectural requirement. The system integrates multiple defensive controls:

1. Password Hashing (Cryptographic Storage)

Plaintext passwords are never stored. User credentials submitted during registration (`register.php`) are hashed using PHP’s native Bcrypt algorithm via password_hash($password, PASSWORD_DEFAULT). Authentication checks in `login.php` utilize password_verify() to compute constant-time cryptographic hash verification, preventing precomputed rainbow table and timing attacks.

Code Listing 3.2: Cryptographic Password Hashing and Verification
// Registration Hashing (register.php)
$hashedPassword = password_hash($password, PASSWORD_DEFAULT);
$stmt = $conn->prepare("INSERT INTO users (username, password, full_name, email, role) VALUES (?, ?, ?, ?, 'user')");
$stmt->bind_param("ssss", $username, $hashedPassword, $full_name, $email);
$stmt->execute();

// Authentication Verification (login.php)
if (password_verify($password, $user['password'])) {
    $_SESSION['user_id'] = $user['id'];
    $_SESSION['role']    = $user['role'];
    // Login successful
}

2. Prepared Statements (SQL Injection Immunity)

To prevent SQL Injection vulnerabilities, all database transactions involving user parameters use MySQLi Prepared Statements. Incoming parameters are separated from query logic and bound as explicit data types (`s` for strings, `i` for integers), rendering SQL syntax injection impossible.

Code Listing 3.3: Parameterized Prepared Statements for Requisition Insertion
// Secure Insertion Guard in student_dashboard.php
$reqStmt = $conn->prepare(
    "INSERT INTO file_requests (student_id, user_id, document_type, purpose, supporting_file, status) 
     VALUES (?, ?, ?, ?, ?, 'Pending')"
);
$reqStmt->bind_param("iisss", $studentRecordId, $userId, $docType, $purpose, $supportingFile);
$reqStmt->execute();
$reqStmt->close();

3. Session Authentication & Role-Based Access Control (RBAC)

Application routing is governed by centralized security guards in `auth_check.php`. Unauthenticated guests attempting direct URL access are immediately redirected to `login.php`. Students attempting to access administrator consoles (`dashboard.php`) are intercepted and redirected to their portal view, while administrators navigating to student self-service routes are redirected to their operational console.

4. Input Validation & Sanitization

All incoming GET and POST parameters are trimmed, cast into typed primitives (e.g., `intval()` for entity identifiers), and sanitized against Cross-Site Scripting (XSS) via htmlspecialchars($var, ENT_QUOTES, 'UTF-8') before rendering into browser DOM trees.

5. Multi-Tier File Upload Validation & Execution Neutralization

Unrestricted file upload is one of the most critical web vulnerabilities. The system enforces a strict 5-step defensive pipeline inside `file_helper.php`:

  • Extension Whitelisting: Files must match explicitly permitted extensions (`jpg`, `jpeg`, `png`, `webp`, `gif` for images; `pdf`, `doc`, `docx`, `xls`, `xlsx`, `csv`, `txt`, `zip` for documents). Executable extensions (`.php`, `.phtml`, `.exe`) are unconditionally rejected.
  • Server-Side MIME Inspection: The server inspects the binary file headers using PHP’s finfo_file() function to verify true MIME signatures, preventing attackers from renaming malicious scripts.
  • Strict Size Constraints: Profile photos are restricted to 3MB; academic documents and attachments are restricted to 5MB.
  • Cryptographic Filename Randomization: Uploaded files are renamed using randomized identifiers combining entity IDs, Unix timestamps, and random bytes (bin2hex(random_bytes(4))).
  • Server Execution Hardening (`.htaccess`): The storage directory (`uploads/`) contains a dedicated Apache `.htaccess` rule that explicitly prohibits server-side script execution.
Code Listing 3.4: Multi-Tier Upload Validation (file_helper.php) & .htaccess
// Multi-Tier File Validation from file_helper.php
function handle_request_attachment_upload(array $file, string $prefix = 'req', ?string &$error = null): string|null|false {
    if (!isset($file['error']) || $file['error'] === UPLOAD_ERR_NO_FILE) return null;
    if ($file['size'] > 5 * 1024 * 1024) { $error = "Exceeds 5MB limit."; return false; }

    $allowedExts = ['pdf', 'doc', 'docx', 'xls', 'xlsx', 'csv', 'txt', 'zip', 'jpg', 'jpeg', 'png', 'webp'];
    $extension = strtolower(pathinfo($file['name'], PATHINFO_EXTENSION));
    if (!in_array($extension, $allowedExts, true)) { $error = "Invalid format."; return false; }

    $fileName = $prefix . "_" . time() . "_" . bin2hex(random_bytes(4)) . "." . $extension;
    move_uploaded_file($file['tmp_name'], UPLOAD_DIR . $fileName);
    return $fileName;
}

# Directory Hardening Directive (uploads/.htaccess)
<FilesMatch "\.(php|phtml|php3|php4|php5|php7|phps|cgi|pl|exe)$">
    Order Deny,Allow
    Deny from all
</FilesMatch>
Options -ExecCGI -Indexes

6. Path Traversal Defense in File Streaming

In `download_file.php`, file parameters are passed through PHP’s basename() function before disk resolution. This removes directory traversal sequences (such as ../ or ..\), preventing unauthorized retrieval of sensitive server configuration files.

Operational evaluation against traditional paper-based workflows demonstrated dramatic improvements in administrative performance:

CHAPTER 5: CONCLUSION AND RECOMMENDATIONS

5.1 What the System Achieved

The Student Request Records System successfully addresses the operational bottlenecks of manual academic document processing. By replacing paper-based requisition slips with an automated, responsive web-based pipeline, the system bridges the communication gap between students and university registrar personnel.

Key achievements include:

  1. Establishment of a secure, authenticated multi-role platform with strict Role-Based Access Control (RBAC) separating administrative controls from student self-service.
  2. Delivery of a transparent, end-to-end document requisition engine featuring real-time lifecycle status badges (Pending, Approved, Rejected) and administrative feedback notes.
  3. Implementation of an administrative management dashboard with comprehensive student CRUD controls, multi-parameter search/filtering, and queue review workflows.
  4. Deployment of secure digital file delivery mechanisms allowing direct retrieval of approved documents.
  5. Enforcement of strict defensive security safeguards, including Bcrypt hashing, parameterized prepared statements, session validation, and multi-tier file upload verification.

5.2 Limitations of the System

While the current release provides robust core functionality, the following technical limitations exist:

  • Absence of Automated Push Notifications: Students must log into the portal to inspect request status; automated SMS or SMTP email alerts are not yet integrated.
  • Manual Clearance Verification: Financial clearances must be verified manually by staff via uploaded receipts rather than real-time payment gateway APIs.
  • Single-Institution Architecture: Designed for single-campus deployment without multi-tenant database partitioning.

5.3 Possible Future Improvements

To expand institutional utility, the following technical enhancements are recommended for future releases:

  1. Automated SMS & Email Notification Gateways: Integration of SMS APIs (e.g., Twilio) and SMTP mailers (e.g., PHPMailer) to dispatch immediate notifications upon status changes.
  2. Digital Payment Gateway Integration: Enabling direct e-wallet (e.g., GCash, PayMaya, PayPal) checkout for transcript fees during requisition submission.
  3. Cryptographic QR Code Verification: Embedding cryptographically signed QR codes onto released digital credentials, enabling employers and external universities to verify document authenticity instantly.
  4. Digital Signature Integration (PKI): Incorporating Public Key Infrastructure (PKI) digital signatures allowing registrar officers to sign approved PDF documents electronically.

CREATE DATABASE IF NOT EXISTS `student_db` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE TABLE `users` (
  `id` INT(11) NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `username` VARCHAR(50) NOT NULL UNIQUE,
  `password` VARCHAR(255) NOT NULL,
  `full_name` VARCHAR(100) NOT NULL,
  `email` VARCHAR(100) NOT NULL,
  `role` VARCHAR(20) NOT NULL DEFAULT 'user',
  `created_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE `students` (
  `id` INT(11) NOT NULL AUTO_INCREMENT PRIMARY KEY,
  `user_id` INT(11) DEFAULT NULL,
  `student_id` VARCHAR(50) NOT NULL UNIQUE,
  `first_name` VARCHAR(100) NOT NULL,
  `last_name` VARCHAR(100) NOT NULL,
  `email` VARCHAR(150) NOT NULL,
  `course` VARCHAR(100) NOT NULL,
  `year_level` INT(11) NOT NULL,
  `status` VARCHAR(50) NOT NULL DEFAULT 'Regular',
  `profile_picture` VARCHAR(255) DEFAULT NULL,
  `record_file` VARCHAR(255) DEFAULT NULL,
  `created_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

  `created_at` TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
